# list-filter-detail — 목록+필터+상세 설계 판정

목록 화면(필터·정렬·검색·페이지)과 상세 왕복이 있는 기능의 **설계 결정 5축**을 판정한다. 정답을 외우는 스킬이 아니라 **신호를 읽고 트레이드오프를 적용하는** 스킬이다 — 각 결정의 "왜"와 "무엇을 포기하는지"는 references/가 근거다.

## 사용 방법 — 이중 모드

1. **판독 먼저.** 아래 신호표의 각 신호를 요청 문장·기획서·기존 코드베이스에서 읽는다. 읽을 수 있는 신호는 **묻지 않는다** — 파악한 것은 "이렇게 이해했다"로 확인만 한다.
2. **판독 불가한 신호만 문답.** 사용자와 대화 중이면 AskUserQuestion 등으로 묻는다(선택지에 트레이드오프를 붙여서). 자율 실행 중이라 물을 수 없으면 각 신호의 **기본값**을 채택하고, 산출물에 "이 신호는 확인 못 해 기본값 사용"을 명시한다.
3. **판정표 적용.** 신호 조합 → 5축 결정. 자기 취향이 아니라 이 문서의 판정을 따른다 — 판정과 다르게 가려면 근거를 사용자에게 확인받는다.
4. **설계 틀 출력.** 아래 출력 형식으로 결정·근거·포기한 것을 제시한 뒤 구현에 들어간다.

## 신호표 — 질문지이자 판독 기준

| # | 신호 | 판독 위치 | 기본값(판독·문답 불가 시) |
|---|------|----------|--------------------------|
| S1 | 필터 상태가 공유·새로고침·뒤로가기에서 복원돼야 하는가 | 기획서 "공유" 언급, 커머스/검색류면 대부분 예 | 예 |
| S2 | SEO가 필요한 데이터인가 (검색 유입 대상) | 마케팅·SEO 요구, 공개 콘텐츠 여부 | 공개 서비스면 예 |
| S3 | 첫 화면(LCP)에 목록 데이터가 보이는가 | 페이지 구조 — 목록이 메인 콘텐츠인가 | 예 |
| S4 | 프레임워크에 서버 렌더 계층이 있는가 (Next.js 등) | package.json·라우터 구조 | — (반드시 판독 가능) |
| S5 | 재방문 캐시가 필요한가 (상세→목록 왕복 잦음) | 상세 페이지 존재 = 대부분 예 | 예 |
| S6 | 최신값이 필수인가 (가격·재고·호가처럼 낡으면 틀린 값) | 도메인 성격 | 아니오 |
| S7 | 필터 탐색이 서비스의 핵심 활동인가 + 뒤로가기=필터 되돌리기 UX를 원하는가 | 커머스 카탈로그·부동산 검색류 | 아니오 |
| S8 | 탐색형 소비인가 (피드처럼 훑어보기, 항목 비교보다 발견) | 도메인 성격·모바일 주력 여부 | 아니오 |
| S9 | 상세가 가볍고 빠른 왕복 비교가 중요한가 (이미지 중심 등) | 상세 콘텐츠 분량 | 아니오 |

## 판정표 — 신호 → 5축 결정

**축 ① 상태 위치** → 상세: `references/state-location.md`

- S1 예(기본): **필터·정렬·검색어·페이지 = URL 쿼리가 단일 진실.** 컴포넌트는 URL에서 파생해 읽기만 한다(내부 상태 복제 금지 — 진실이 둘이면 뒤로가기에서 화면≠주소가 된다).
- 연속 입력(슬라이더·타이핑)만 로컬 에코: 즉시 그리고 디바운스 후 URL 반영.
- 히스토리: **기본 replace**, S7 예면 이산 변경에 push.
- URL 금지 4종: 임시 UI 상태 / 민감 정보 / 타이핑 중간값(디바운스 전) / 대용량 선택(서버 저장+ID 참조).
- Next.js 서버 컴포넌트 환경: `window.history.replaceState`로 서버 왕복 없이 URL 갱신.

**축 ② 데이터 페칭** → 상세: `references/data-fetching.md` (5분기 판정)

- CSR + 소규모·캐시 불필요·**요청 경쟁 없음**: fetch+상태
- CSR + 캐시·경쟁·폴링 중 하나라도 필요: TanStack Query — S6(최신값 필수)은 fetch+상태의 근거가 아니라 **TQ + staleTime: 0/refetchInterval**의 근거다
- Next.js + S2·S3(SEO·LCP): 서버 컴포넌트/SSR로 초기 렌더
- Next.js + 초기는 서버, 이후 필터 변경 재요청: **서버 컴포넌트 초기 데이터 → TQ 하이드레이션** (이 케이스의 표준 조합)
- 필터 있는 목록은 "필터 연타 → 이전 응답이 늦게 도착해 덮어씀" 경쟁 상태가 대표 버그다 — fetch+상태를 고르면 AbortController를 직접 짜야 함을 경고하라.

**축 ③ 목록 넘김** — 기본 **페이지네이션**(URL에 page가 실려 공유·복원·SEO·푸터 접근이 공짜). S8 예면 무한스크롤 — 단 스크롤 복원·"돌아가기 어려움" 비용을 함께 제시.

**축 ④ 상세 진입** — 기본 **별도 라우트**(/items/:id). S9 예면 모달/시트 — 단 **모달이어도 URL은 바꾼다**(공유·새로고침 시 전체 페이지로 열리게).

**축 ⑤ 복귀 복원** — 필터·페이지는 축 ①의 URL 진실로 공짜. **스크롤 위치는 캐시 전략의 결과물**이다: 복귀 시 캐시 히트(TQ)로 즉시 렌더되면 브라우저 복원이 동작하고, 무한스크롤이면 sessionStorage에 위치+로드 분량 기록이 추가로 필요하다. → `references/list-navigation.md`

## 출력 형식 — 설계 틀

판정을 마치면 구현 전에 이 형식으로 제시한다:

```
## 설계 판정: {기능명}
| 축 | 결정 | 근거(신호) | 포기하는 것 |
|----|------|-----------|------------|
| 상태 위치 | URL 쿼리 단일 진실 | S1 공유 필요 | 스토어 대비 초기 파싱 코드 |
| ... | | | |
확인 못 한 신호: {있으면 — 기본값 채택 사실 명시}
```

사용자가 대화 중이면 이 표를 승인받고 구현, 자율 실행이면 표를 산출물에 남기고 진행한다.

## 주의사항

- 이 스킬은 **설계 판정까지**다 — UI 구현 패턴(무한스크롤 IntersectionObserver, 스켈레톤 등)은 fe-ui 스킬(scroll-reveal·skeleton 등)이 담당한다.
- 판정표에 없는 신호 조합을 만나면 references/의 트레이드오프 원리로 돌아가 추론하고, 그 판단을 출력에 명시한다.
- 인증·권한이 걸린 목록(마이페이지 주문 내역 등)도 같은 판정이 적용되나, URL 금지 4종의 민감 정보 항목을 특히 점검하라.
