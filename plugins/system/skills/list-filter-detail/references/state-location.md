## 1. 왜 URL이 기본인가

필터·정렬·검색어·페이지를 URL 쿼리에 두면 다음이 **추가 코드 없이** 따라온다:

- **공유** — 링크를 받은 사람이 같은 화면을 본다 (기획서에 "공유"가 없어도 사용자는 주소창을 복사한다)
- **새로고침·재방문 복원** — 브라우저가 해준다
- **뒤로가기/앞으로가기** — 히스토리가 상태 히스토리가 된다
- **서버 렌더링 호환** — 서버가 요청 URL만 보고 같은 화면을 그릴 수 있다 (SEO의 전제)

이걸 스토어(Zustand 등)에 두면 위 네 가지를 전부 손으로 재구현하거나 포기해야 하고, "탭을 닫았다 열었는데 지난 필터가 남아 있는" 유령 상태 문제가 따라온다. 컴포넌트 상태에 두면 새로고침에 전부 증발한다.

**포기하는 것**: URL 파싱·직렬화 코드(§6), 타입 안전성(쿼리는 문자열 — 파서에서 검증), URL 길이 한계(§5).

## 2. 왜 "내부 상태 + URL 미러"가 아닌가

"초기 URL을 내부 상태의 시드로 쓰고, 변경 시 URL을 미러로 갱신"하는 설계는 **진실을 둘로** 만든다:

```
1. 필터 A → B 변경   내부: B / URL: ?f=B   ✓ 일치
2. 사용자가 뒤로가기   URL: ?f=A (브라우저)
                      내부: B (아무도 안 알려줌)   ✗ 화면 ≠ 주소
```

이 순간 화면은 B인데 주소는 A — 이 주소를 복사해 공유하면 받는 사람은 A를 본다. 막으려면 popstate를 수신해 URL→내부 역동기화를 해야 하고, 그 순간 "미러"가 아니라 양방향 동기화 기계가 된다(코드·버그 표면 증가). **URL에서 파생해 읽으면(useSearchParams) 이 문제가 존재하지 않는다.**

## 3. 로컬 에코 — 연속 입력의 예외

슬라이더 드래그·검색어 타이핑은 키스트로크마다 URL을 갱신하면 히스토리 오염·성능 문제가 생긴다. 규칙:

- 연속 입력 **중**: 로컬 상태로 즉시 그린다 (입력 반응은 프레임 단위여야 한다)
- 입력이 **멎으면**(디바운스 250~400ms) 또는 **확정되면**(엔터·드래그 종료): URL에 반영
- URL 반영 순간부터 다시 URL이 진실 — 로컬 에코는 입력 중의 잔상일 뿐 저장소가 아니다

## 4. push vs replace

| 정책 | 효과 | 언제 |
|------|------|------|
| **replace (기본)** | 필터 변경이 히스토리를 쌓지 않음 — 뒤로가기는 목록 이전 페이지로 이탈 | 대부분. 필터 5번 바꾸고 뒤로가기 5번 눌러야 목록을 벗어나는 "히스토리 오염" 방지 |
| push (신호 시) | 뒤로가기 = 필터 되돌리기 | 필터 탐색이 서비스의 핵심 활동(커머스 카탈로그·부동산 검색)이고 그 UX를 명시적으로 원할 때. 이산 변경(클릭)에만 — 연속 입력은 여전히 replace |

## 5. URL 금지 목록

| 금지 | 이유 | 대신 |
|------|------|------|
| 임시 UI 상태 (패널 열림, 드롭다운) | 공유받은 사람에게 재현될 이유가 없는 순간 상태 — 히스토리만 오염 | 컴포넌트 상태 |
| 민감 정보 (식별자·토큰·개인정보) | URL은 로그·히스토리·공유로 유출되는 공개 표면 | 세션/서버 상태 |
| 타이핑 중간값 | 키스트로크마다 히스토리 폭발 | 로컬 에코 + 디바운스 후 반영 (§3) |
| 대용량 선택 목록 (체크박스 수백 개) | URL 실질 한계 ~2000자 | 서버 저장 + ID 참조 |

## 6. 인코딩 규약

- **기본값은 생략한다** — `?sort=recommended`처럼 기본값을 실으면 모든 URL이 길어지고 "기본 상태" URL이 두 개가 된다. 기본값이면 키 자체를 지운다.
- 다중 선택은 반복 키(`?cat=a&cat=b`) 또는 구분자(`?cat=a,b`) 중 하나로 통일하고 파서와 짝을 맞춘다.
- 파서는 **불신 입력**으로 다룬다 — 범위 밖 값·이상한 타입은 기본값으로 강등(사용자가 URL을 손으로 고칠 수 있다).

## 7. 프레임워크별 갱신 수단

| 환경 | 읽기 | 갱신(리로드 없음) |
|------|------|------------------|
| React Router | `useSearchParams()` | `setSearchParams(p, { replace: true })` |
| Next.js App Router (클라이언트) | `useSearchParams()` | `router.replace(...)` — 단 서버 컴포넌트가 searchParams를 읽으면 **서버 왕복(RSC refetch) 발생** |
| Next.js 14.1+ (왕복 회피) | 〃 | `window.history.replaceState(null, '', url)` — 공식 지원, 서버 왕복 없이 URL만 갱신. 클라이언트에서 데이터를 다시 그리는 경우에 사용 |
| 바닐라 | `new URLSearchParams(location.search)` | `history.replaceState` + 직접 렌더 |

주의: CSR(SPA 라우터)에서 setSearchParams는 원래 리로드 없이 리렌더만 한다 — "URL 바꾸면 깜빡인다"는 걱정은 서버 컴포넌트 왕복 환경에서만 실재한다.
