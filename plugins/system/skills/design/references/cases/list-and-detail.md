# 케이스: 목록 + 필터 + 상세

상품 목록·검색 결과·게시판처럼 **필터/정렬/검색이 있는 목록과 상세 화면을 오가는** 흐름. `core-questions.md` C1~C8을 먼저 진행하고 아래를 얹는다.

---

## L1. 필터 상태를 URL에 둘까 — 확정형(공개 서비스) / 추천형(그 외)

**공유·새로고침·뒤로가기에서 필터가 살아야 하면 URL 쿼리가 유일한 진실이다.** 컴포넌트는 URL에서 읽기만 하고 내부 상태로 복제하지 않는다 — 진실이 둘이면 뒤로가기에서 화면과 주소가 어긋난다.

- 연속 입력(슬라이더·타이핑)만 로컬로 즉시 그리고, 잠시 뒤(디바운스) URL에 반영한다.
- 히스토리는 **기본 replace**. 단 필터 탐색 자체가 서비스의 핵심 활동이고 "뒤로가기 = 직전 필터로"를 원하면 이산적 변경에만 push.
- **URL 금지 4종**: 임시 UI 상태 / 개인정보·토큰 / 타이핑 중간값 / 대용량 선택(서버 저장 후 ID 참조).
- Next.js 서버 컴포넌트 환경에서는 `window.history.replaceState`로 서버 왕복 없이 URL만 갱신할 수 있다.

근거: `topics/state-location.md`

## L2. 데이터를 어떻게 가져올까 — 추천형

5분기 판정과 근거는 `topics/data-fetching.md`. 요약:

| 상황 | 선택 |
|------|------|
| CSR + 소규모 + 캐시·경쟁·폴링 불필요 | `fetch` + 상태 |
| CSR + 캐시·경쟁·폴링 중 하나라도 필요 | TanStack Query |
| Next.js + SEO·첫 화면 콘텐츠 | 서버 컴포넌트/SSR |
| Next.js + 초기는 서버, 이후 필터 변경 재요청 | **서버 컴포넌트 초기 데이터 → TQ 하이드레이션** (이 케이스의 표준) |

- "최신값이 반드시 필요"는 `fetch`+상태의 근거가 **아니다** — TQ + `staleTime: 0`/`refetchInterval`의 근거다.
- **필터 연타 → 이전 응답이 늦게 도착해 최신 결과를 덮어씀**이 이 케이스의 대표 버그다. `fetch`+상태를 고르면 `AbortController`를 직접 짜야 한다는 점을 고지한다.

## L3. 목록을 어떻게 넘길까 — 추천형

➡️ 기본 **페이지네이션**. `page`가 URL에 실려 공유·복원·SEO·푸터 접근이 공짜다.
➡️ 훑어보는 소비(피드형)면 무한스크롤 — 대신 스크롤 복원 비용과 "특정 지점으로 돌아가기 어려움"을 함께 제시한다. 채택하면 `cases/feed.md`로 넘어간다.
➡️ SEO가 필요한 콘텐츠에 무한스크롤을 얹으면 크롤러가 뒷페이지를 못 본다 — 이 조합은 반드시 사용자에게 확인받는다.

## L4. 상세로 어떻게 들어갈까 — 추천형

➡️ 기본 **별도 라우트**(`/items/:id`).
➡️ 상세가 가볍고 빠른 왕복 비교가 중요하면 모달/시트. 단 **모달이어도 URL은 바꾼다** — 공유·새로고침 시 전체 페이지로 열려야 한다.

## L5. 목록으로 돌아왔을 때 — 확정형

필터·페이지는 L1의 URL 진실로 자동 복원된다. **스크롤 위치는 캐시 전략의 결과물이다** — 복귀 시 캐시 히트로 즉시 렌더되면 브라우저 복원이 동작하고, 무한스크롤이면 sessionStorage에 위치와 로드 분량을 따로 기록해야 한다.

근거: `topics/list-navigation.md`

---

## 이 케이스에서 자주 나는 사고

- 필터를 상태와 URL 양쪽에 두어 뒤로가기 시 화면 ≠ 주소
- 필터 연타 시 옛 응답이 최신 결과를 덮어씀
- 상세 갔다 돌아오면 스크롤이 맨 위로
- 모달 상세에 URL이 없어 링크 공유가 불가
