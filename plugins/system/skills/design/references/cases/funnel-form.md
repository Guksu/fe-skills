# 케이스: 퍼널 폼 (여러 단계로 나뉜 입력 흐름)

주문·결제, 회원가입, 온보딩, 설문, 어드민 등록 마법사 — **화면을 여러 번 넘기며 입력을 받고 마지막에 한 번 제출하는** 모든 흐름. 단계가 있고 중간 이탈이 가능하면 도메인이 무엇이든 이 케이스다.

`core-questions.md`의 C1~C8을 먼저 진행하고, 아래 질문을 얹는다. F0(도메인 갈래)이 나머지 대부분을 좌우하므로 **가장 먼저** 확정한다.

---

## F0. 도메인 갈래 — 추천형 (가장 먼저)

| 갈래 | 예 | 성격 |
|------|-----|------|
| **거래형** | 주문·결제, 보험 가입, 대출 신청 | 돈·계약. 중복 제출이 곧 사고 |
| **계정형** | 회원가입, 온보딩, 본인확인 | 한 번 하고 끝. 중간 이탈이 잦음 |
| **수집형** | 설문, 신청서, 예약 | 한자리에서 끝내는 게 정상 |
| **내부도구형** | 어드민 등록 마법사, 대량 업로드 | 숙련 사용자. 되돌리기·검증이 우선 |

➡️ 요청·기획서에서 대부분 읽힌다. 애매하면 "돈이나 계약이 걸리나 / 나중에 이어서 하는 게 흔한가" 두 가지로 좁혀 묻는다. 갈래가 걸치면(온보딩 중 결제) **더 엄격한 쪽**(거래형)을 적용한다.

## F1. 단계 상태를 어디에 보관할까 — 추천형

1단계에서 받은 값을 마지막까지 들고 가야 한다. 어디에 둘까.

- **A: 브라우저** (메모리 + sessionStorage) — 프론트 단독으로 끝남 / 기기를 바꾸면 사라지고, 재고 선점 같은 건 못 함
- **B: 서버 임시저장**(드래프트 생성 API) — 새로고침·기기 변경·이어서하기에 강함 / 백엔드 협의 비용, 만료·정리 정책 필요

➡️ 갈래별 추천:

| 갈래 | 추천 | 단서 |
|------|------|------|
| 거래형 | **B(서버)** | 드래프트 API가 없으면 A로 후퇴하되, 최종 제출 시 서버 생성 + F5 멱등키를 반드시 건다 |
| 계정형 | **B(서버)** | 로그인 이전 단계라 저장 주체가 없으면 A |
| 수집형 | **A(브라우저)** | 응답이 길면(10분 이상) B 검토 |
| 내부도구형 | **A(브라우저)** | 대량 입력이면 자동 저장 추가 |

➡️ 어느 쪽이든 **저장 제외 목록은 별도로 정한다** → F4(c).

## F2. 단계마다 URL을 나눌까 — 확정형

**나눈다.** `/checkout/shipping` → `/checkout/payment`처럼 단계마다 경로를 준다. 단일 URL에서 화면만 교체하면 뒤로가기가 폼 전체를 닫아버리고, 새로고침에 단계가 사라지며, 어느 단계에서 이탈했는지도 못 본다.

함께 못박는 가드 2개:

1. **선행 미완료 진입 차단** — 3단계 URL로 바로 들어왔는데 1·2단계가 안 끝났으면 **끝난 마지막 단계로 되돌린다**(에러 화면 금지).
2. **완료 후 되돌아가기 차단** — 제출 완료 화면으로 갈 때 히스토리를 **교체**(`replace`)해, 뒤로가기로 결제 화면에 다시 못 들어가게 한다.

➡️ 예외를 두려면 사용자 근거가 필요하다. 흔한 반례는 모달 안에서 도는 3단계 이하 짧은 흐름 — 이때만 단일 URL을 허용하고, 대신 뒤로가기 = 모달 닫기임을 합의한다.

## F3. 값 검사를 어떻게 나눌까 — 추천형

- **A: 단계별 스키마 + 최종 합성** — 단계마다 검사 규칙을 따로 정의하고, 마지막 제출 직전에 전부 합쳐 한 번 더 검사
- **B: 전체 스키마 하나** — 하나를 만들고 단계마다 필요한 부분만 골라 검사

➡️ **A 추천** (예시: `zod` 스키마를 단계별로 정의, 최종은 `stepSchemas.reduce(merge)`). 단계 구성이 갈래·기획마다 달라지므로 단계별 정의가 변경에 강하다. 다만 **최종 합성 검사를 빠뜨리지 마라** — 뒤로 갔다가 값을 바꾸고 다른 경로로 제출되는 흐름에서 구멍이 난다.

➡️ 검사 **시점**(추천형): 처음엔 검사하지 않고 → "다음" 클릭 시 첫 검사 → 한 번 틀린 칸부터 입력 중 실시간(`react-hook-form`의 `mode: 'onTouched'` 계열). 입력도 하기 전에 빨간 글씨를 뿌리면 이탈이 는다.

➡️ **확정형: 프론트 검사는 편의일 뿐이다.** 최종 제출은 서버가 반드시 다시 검사하고, 거래형은 **가격·재고·쿠폰을 제출 시점에 재확인**한다(장바구니에 담은 뒤 값이 바뀐다).

## F4. 나갔다 돌아왔을 때 이어서 하기 — 추천형 (전부 문답)

기간·동작이 도메인과 기획에 따라 갈린다. **기본값으로 때우지 말고 묻는다.**

**(a) 복귀 지점** — 마지막 완료 단계의 다음으로 바로 보낼지, 1단계부터 값만 채워둘지, "이어서 하시겠어요?"를 물을지. 시간 기준을 둘 거면 그 기준도 기획에서 받는다.

**(b) 보관 기간** — 며칠인지, 세션 한정인지. 서버 저장이면 만료·정리 주체가 서버인지 확인하고, 브라우저 저장이면 저장 시각을 함께 적어 읽을 때 검사한다.

**(c) 저장 제외 목록** — **확정형 최소선: 카드번호·CVC·비밀번호·주민등록번호는 브라우저·서버 임시저장 어디에도 남기지 않는다.** 그 외에 무엇을 제외할지는 기획·법무 요건을 사용자에게 확인해 목록으로 확정한다(추천 없이 묻는다 — 필수 확인형).

## F5. 제출 안전 — 갈래에 따라 강도가 다름

- **거래형: 확정형.** 클라이언트가 발급한 **멱등키**를 최종 제출 요청에 실어 보내고, 재시도에도 같은 키를 쓴다. 응답을 못 받은 경우(네트워크 끊김)는 재제출이 아니라 **주문 조회로 결과를 확인**한다. 버튼 비활성화는 보조 수단일 뿐 안전장치가 아니다.
- **계정형: 추천형.** 서버 유니크 제약(이메일 등)이 이미 중복을 막으면 멱등키까지는 과할 수 있다. 다만 결제·유료 전환이 섞이면 거래형으로 올린다.
- **수집형·내부도구형: 추천형.** 제출 중 버튼 잠금 + 성공 시 폼 초기화로 충분한 경우가 많다.
- 공통: **자동 무한 재시도 금지**, 실패 시 사용자가 누르는 재시도. 근거는 `topics/submit-safety.md`.

## F6. 앞 단계로 돌아가 고치기 — 추천형

마지막 확인 화면에서 "배송지가 틀렸다"를 어떻게 처리할까.

- **A: 해당 단계로 점프 → 저장하면 확인 화면으로 자동 복귀** — 단계가 많아도 일관됨 / 이동이 두 번 보임
- **B: 확인 화면에서 인라인 편집** — 이동이 없음 / 검사 규칙이 두 곳에 생겨 어긋나기 쉬움

➡️ **A 추천.** F3에서 단계별 스키마를 쓰기로 했다면 A가 그 구조를 그대로 재사용한다. B를 고르면 인라인 편집도 **같은 단계 스키마**를 쓰도록 못박는다.

## 이 케이스에서 자주 나는 사고

- 완료 화면에서 뒤로가기 → 결제 화면 재진입 → 이중 결제 (F2 가드 2)
- 결제 성공했는데 응답 유실 → 사용자가 다시 누름 → 주문 2건 (F5 멱등키)
- 이어서하기를 만들며 카드번호까지 저장 (F4-c)
- 장바구니에 담을 때 가격으로 결제 → 그사이 가격 변경 (F3 제출 시 재확인)
- 단계별 검사만 하고 최종 합성 검사 누락 → 뒤로 가서 값 바꾼 뒤 제출되는 구멍 (F3)

## 이 케이스가 아닌 것

- 단일 화면 폼(로그인·문의) — 단계가 없으면 `core-questions.md`만으로 충분하다.
- 단계 전환 애니메이션·진행 표시 UI — fe-ui 스킬 담당.
