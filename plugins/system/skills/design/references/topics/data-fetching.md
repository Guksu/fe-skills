## 1. 5분기 판정 트리

| # | 환경·조건 | 권장 |
|---|----------|------|
| 1 | CSR + 소규모 + 재방문 캐시 불필요 + **요청 경쟁 없음** | fetch + 상태 (의존성 0) |
| 2 | CSR + 캐시·경쟁·폴링 중 하나라도 필요 | TanStack Query |
| 3 | Next.js + 해외 사용자 비중 큼 + 서버 경유가 사용자 왕복보다 유리(§2 대리 신호로 판정) | 서버 컴포넌트 초기 렌더. 불리하면 캐시 여부 따라 2번/1번 |
| 4 | Next.js + 서버 컴포넌트 리딩이 빠르고 기획상 초기 노출 필요 | 서버 컴포넌트 |
| 5 | Next.js + 국내 위주: SEO 필요 데이터 | 서버 컴포넌트/SSR. SEO 불필요면 TanStack Query(브라우저 요청) |

분기 1의 조건 세 개는 **전부** 충족해야 한다 — 특히 "요청 경쟁 없음"(§3). 하나라도 깨지면 2번이다.

## 2. 대리 신호 — "왕복 시간"을 판독 가능하게

"서버 왕복이 사용자 직접 요청보다 빠른가"는 코드에서 읽을 수 없다(인프라·CDN·유저 위치 의존). 판독 가능한 대리 신호로 근사한다:

- **SEO 크롤러 요구** — 타깃 검색엔진이 JS 렌더링을 보장하지 않으면(또는 보장이 불안정하면) 서버 렌더가 필요하다 → 분기 5의 "SEO 필요"
- **첫 화면(LCP)에 포함** — 목록이 페이지의 메인 콘텐츠면 서버 렌더가 체감 로딩을 줄인다
- **데이터 소스 리전** — API 서버가 렌더 서버와 같은 리전이면 서버 경유가 싸다 (배포 설정·환경변수에서 추정 가능)

셋 다 판독 불가하고 문답도 불가하면: SEO·LCP 기본값 "예"(공개 서비스 가정)로 서버 렌더 쪽을 택하고 그 사실을 명시한다.

## 3. 경쟁 상태 — 이 케이스의 대표 버그

필터 있는 목록의 고전 버그: 사용자가 필터를 연타 → 요청 A(느림)·B(빠름)가 순서 역전 → **B 화면 위에 A 응답이 덮어써짐**. 

- fetch+상태로 가면 AbortController로 이전 요청을 취소하는 코드를 직접 짜야 한다 — 분기 1을 고를 때 이 비용을 반드시 경고하라.
- TanStack Query는 쿼리 키(`['items', filters]`)가 바뀌면 이전 요청 결과를 현재 화면에 반영하지 않는다 — 경쟁 상태가 구조적으로 사라진다. 필터 목록에서 TQ를 기본으로 미는 실질적 이유가 이것이다.

## 4. "최신값 필수"의 올바른 해석

"가격·재고·호가처럼 낡으면 틀린 값"은 **캐시를 버릴 이유가 아니라 캐시 정책을 조일 이유**다:

- `staleTime: 0` — 항상 낡은 것으로 간주해 재검증
- `refetchInterval` — 폴링 (호가류)
- 진짜 실시간이면 웹소켓 구독 계층 + TQ 캐시에 반영

fetch+상태로 가도 이 요구(폴링·중복 제거·포커스 갱신)는 사라지지 않고 손으로 짜게 될 뿐이다. "최신값 필수 → fetch+상태"로 매핑하지 마라.

## 5. 표준 조합 — 서버 초기 + TQ 하이드레이션

목록+필터+상세 케이스에서 초기 진입은 서버(SEO·LCP), 이후 필터 변경은 클라이언트 재요청인 경우가 대부분이다. 이때:

1. 서버 컴포넌트가 URL searchParams로 초기 목록을 렌더
2. 클라이언트 TQ에 `initialData`(또는 Hydration 경계)로 이어받기
3. 이후 필터 변경은 축 ①의 URL 갱신 → TQ 쿼리 키 변경 → 클라이언트 페칭

서버 왕복을 초기 1회로 제한하면서 SEO·캐시·경쟁 방지를 모두 얻는다. 비용: 서버/클라이언트 두 곳의 페칭 코드와 쿼리 키·URL 파서를 짝 맞춰야 한다(파서를 공용 모듈로 분리하라).
