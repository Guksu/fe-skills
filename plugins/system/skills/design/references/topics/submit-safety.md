# 제출 안전 — 중복 실행과 응답 유실

돈·계약·발송·차감처럼 **두 번 실행되면 안 되는 요청**을 다룬다. 퍼널 폼(`cases/funnel-form.md` F5)의 근거 문서.

## 문제는 "두 번 누름"이 아니다

버튼 더블클릭은 증상 중 하나일 뿐이고, 비활성화로 막을 수 있는 것도 그것뿐이다. 실제로 주문이 두 건 생기는 경로는 이렇다.

1. 사용자가 제출 → 서버가 주문 생성 성공 → **응답이 오는 길에 네트워크가 끊김**
2. 클라이언트는 실패로 판단하고 "다시 시도" 표시
3. 사용자가 다시 누름 → 서버는 새 요청으로 보고 주문을 하나 더 만든다

클라이언트는 "요청이 서버에 닿지 않은 것"과 "닿았는데 응답만 유실된 것"을 **구분할 수 없다.** 그래서 클라이언트 쪽 가드만으로는 절대 해결되지 않는다.

## 멱등키 — 서버가 같은 요청임을 알아보게 한다

멱등(idempotent)은 "몇 번을 실행해도 결과가 같다"는 뜻이다. 요청마다 고유값(멱등키)을 붙이고, 서버가 그 키를 기억해 **같은 키의 두 번째 요청에는 새로 만들지 않고 첫 번째 결과를 그대로 돌려주게** 한다.

규칙:

- **키는 클라이언트가 만든다.** 서버가 만들면 재시도 때 새 키를 받게 되어 의미가 없다. `crypto.randomUUID()`로 충분하다.
- **키의 수명은 "이 제출 시도"다.** 최종 제출 화면에 진입할 때 한 번 만들어 상태에 보관하고, 재시도에는 **같은 키**를 쓴다. 사용자가 폼을 고쳐 새로 제출하는 것은 새 시도이므로 새 키를 발급한다.
- 키는 `Idempotency-Key` 헤더나 본문 필드로 보낸다. **백엔드와 반드시 합의해야 동작한다** — 프론트만 붙이면 아무 효과가 없다. 합의가 안 되면 그 사실을 결정 기록의 "확인하지 못한 것"에 남긴다.
- 보관 기간도 합의 항목이다(보통 24시간~며칠). 그 기간이 지나면 같은 키도 새 요청으로 처리된다.

## 응답을 못 받았을 때 — 재제출이 아니라 조회

네트워크 오류로 응답을 못 받으면 **같은 키로 재시도**하거나, 조회 API로 결과를 확인한다("이 멱등키/주문번호로 생성된 주문이 있는가"). 사용자에게는 "결제가 완료됐는지 확인 중"으로 보여주고, 확인 전에는 재시도 버튼을 잠근다.

## 하지 말 것

- **자동 무한 재시도.** 사용자는 상황을 모른 채 서버만 두들기고, 멱등키가 없다면 그만큼 사고가 커진다. 재시도는 사용자가 누르게 한다.
- **버튼 비활성화를 안전장치로 신뢰하기.** 새로고침 후 재제출, 두 탭 동시 제출, 뒤로가기 재진입에는 무력하다. 보조 수단으로만 쓴다.
- **낙관적 업데이트로 완료 화면 먼저 보여주기.** 거래형에서는 서버 확정 응답 전에 완료를 보여주지 않는다.

## 갈래별 강도

| 갈래 | 필요한 것 |
|------|----------|
| 거래형(결제·계약) | 멱등키 필수 + 조회로 복구 + 완료 화면 히스토리 replace |
| 계정형 | 서버 유니크 제약으로 충분한 경우가 많음. 유료 전환이 섞이면 거래형으로 승격 |
| 수집형·내부도구형 | 제출 중 잠금 + 성공 시 초기화로 대개 충분 |
