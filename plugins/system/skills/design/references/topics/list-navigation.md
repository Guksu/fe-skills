## 1. 축 ③ 페이지네이션 vs 무한스크롤

**기본: 페이지네이션.** URL에 `page`가 실리므로 공유·복원·SEO·"어디까지 봤는지"·푸터 접근이 전부 공짜다.

**무한스크롤 신호**: 탐색형 소비(항목 비교보다 발견 — 피드류) + 모바일 주력. 선택 시 함께 떠안는 비용을 명시하라:

- 스크롤 복원을 직접 설계해야 함 (§3)
- "300번째 항목으로 돌아가기"가 어려움 — 상세 왕복이 잦으면 최악의 조합
- 푸터가 닿을 수 없는 곳이 됨
- URL로 위치를 표현할 수 없어 공유가 "처음부터"로 열림

절충이 필요하면 "더보기 버튼"(사용자 의도 로드)이 중간값이다 — 단 URL 복원은 여전히 안 된다.

## 2. 축 ④ 상세 진입 — 라우트 vs 모달

**기본: 별도 라우트** (`/items/:id`). 공유·SEO·새로고침·뒤로가기가 공짜.

**모달 신호**: 빠른 왕복 비교가 중요 + 상세가 가벼움(이미지 중심) + 개별 공유 요구 적음.

**모달이어도 URL은 바꾼다** — 모달을 열 때 `/items/:id`로 pushState하고, 그 URL로 직접 진입(공유·새로고침)하면 전체 페이지로 연다. 목록 위 모달은 "목록 맥락에서 열었을 때"의 표현일 뿐, 주소 없는 화면을 만들지 않는다. (인터셉팅 라우트 — Next.js App Router는 이 패턴을 프레임워크 수준에서 지원)

## 3. 축 ⑤ 복귀 복원 — 필터·페이지·스크롤

"돌아왔다"고 느끼려면 세 가지가 복원돼야 한다:

| 대상 | 복원 수단 | 비용 |
|------|----------|------|
| 필터·정렬·검색어 | 축 ①의 URL 진실 — 뒤로가기가 곧 복원 | 0 (이미 설계됨) |
| 페이지 | URL의 page 파라미터 — 동일 | 0 |
| 스크롤 위치 | 아래 참조 | 캐시 전략에 따라 다름 |

**스크롤 복원은 캐시 전략의 결과물이다:**

- 브라우저의 기본 스크롤 복원은 **복귀 시점에 콘텐츠가 이미 그 높이만큼 그려져 있어야** 동작한다. 복귀했는데 로딩 스피너부터 돌면 복원할 지점이 없다.
- 따라서 페이지네이션 + TQ 캐시 히트(복귀 시 즉시 렌더)면 **자동으로 동작한다** — 별도 설계 불필요. 이것이 축 ②에서 캐시를 요구한 숨은 이유다.
- **무한스크롤이면 추가 설계가 필요하다**: sessionStorage에 (스크롤 위치, 로드한 분량)을 기록하고, 복귀 시 그 분량을 캐시에서 즉시 재렌더한 뒤 위치로 점프. TQ `useInfiniteQuery`의 캐시가 로드 분량을 이미 들고 있으므로 위치만 기록하면 된다.
- 상세를 모달(축 ④)로 열었다면 목록이 언마운트되지 않으므로 이 문제 전체가 사라진다 — 모달 신호가 강한 또 하나의 이유.
