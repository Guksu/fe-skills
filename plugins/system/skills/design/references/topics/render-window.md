# 렌더 윈도우 — 무한 누적을 3단으로 다스린다

## 문제의 실체

30분 스크롤이면 카드 수백~수천 개가 DOM에 쌓인다. 비용은 셋이다: DOM 노드 자체(스타일·레이아웃 계산 대상 증가), 디코딩된 이미지 메모리(뷰포트 밖이어도 DOM에 있으면 유지될 수 있다), 스크롤마다 커지는 렌더 트리 갱신. 미디어 피드일수록 이미지 메모리가 지배적이다 — 화면 밖 이미지를 DOM에서 떼어내면 브라우저가 디코딩 메모리를 회수한다.

## 3단 판정 — 최적화는 공짜가 아니다

| 단계 | 채택 신호 | 수단 | 비용 |
|------|----------|------|------|
| 아무것도 안 함 | 수십 개 규모(끝이 있는 짧은 피드) | — | 없음 — 이 단계에서 가상화는 과설계다 |
| 렌더 스킵 | 수백 개 또는 미디어 중심 | `content-visibility: auto` + `contain-intrinsic-size` | DOM·JS 메모리는 계속 쌓인다 |
| 가상화 | 수천 개·초장기 세션(SNS 홈급) | 동적 측정 가상화 (TanStack Virtual 등) | 라이브러리·측정 복잡도, 아래 포기 목록 |

### 2단: content-visibility

```css
.feed-card {
  content-visibility: auto;
  contain-intrinsic-size: auto 320px; /* 화면 밖일 때 쓸 추정 높이 */
}
```

화면 밖 카드의 렌더링(스타일·레이아웃·페인트)을 브라우저가 스킵한다. 라이브러리 없음, 스크롤 점프 없음, 접근성 트리 유지. DOM은 남으므로 노드 수 자체의 누적은 못 막는다 — "수천 개" 신호가 켜지면 3단으로.

### 3단: 동적 측정 가상화

피드 카드는 이미지 비율·텍스트 길이로 높이가 제각각이라 고정 높이 가상화가 성립하지 않는다. 동적 측정 방식은:

1. **추정 높이**로 전체 스크롤 높이·위치를 계산하고
2. 실제 렌더된 아이템을 **실측**(ResizeObserver / `measureElement`)해
3. 추정 오차를 **보정**한다.

부작용은 **위로 스크롤할 때의 점프** — 위쪽 아이템의 추정이 틀렸던 만큼 보정 순간 화면이 튄다. 완화책: 이미지 `aspect-ratio` 사전 지정으로 추정 정확도를 올린다(CLS 개선과 같은 수단), 텍스트 잘라내기 정책으로 높이 분산을 줄인다.

## 오버스캔 — 개수가 아니라 뷰포트 단위

뷰포트 밖을 미리 그려두는 버퍼(오버스캔)는 "±3개"처럼 개수로 잡으면 카드 높이에 따라 의미가 달라진다. **±1~2 뷰포트 높이**로 잡는다. 빠른 플릭에서 빈 영역이 잠깐 보이는 것은 버그가 아니라 수용하는 트레이드오프다(대형 SNS도 동일) — 빈 영역에는 스켈레톤을 깐다(구현은 fe-ui `skeleton` 스킬).

## 가상화가 포기하는 것 — 채택 시 사용자에게 고지

- 브라우저 페이지 내 찾기(Ctrl+F)가 화면 밖 항목을 못 찾는다.
- 화면 밖 항목이 접근성 트리에 없다 — 스크린리더가 전체 목록을 인지하지 못한다.
- 스크롤바 위치·높이가 추정 기반이라 미세하게 출렁일 수 있다.
