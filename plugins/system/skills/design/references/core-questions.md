# 범용 질문 뼈대 — 모든 화면에 성립하는 8개

케이스 파일이 없어도 이 8개는 묻는다. 케이스 파일이 있으면 이 뼈대 위에 케이스 질문을 얹는다(중복은 케이스 쪽 서술이 우선).

순서에 의미가 있다. **C1~C3이 나머지를 결정**하므로 먼저 묻고, C4 이후는 앞의 답에 따라 내용이 달라진다 — 한 라운드에 몰아 묻지 마라.

---

## C1. 이 화면이 하는 일과 성공 기준 — 필수 확인형

무엇을 만드는지, 그리고 **무엇이 되면 성공인지**. "주문 페이지"는 요구사항이 아니다. "비회원도 3분 안에 결제까지 끝낸다"가 요구사항이다.

같이 확정할 것: 사용자가 누구인가(일반 사용자/내부 직원) · 주 디바이스(모바일 웹/데스크톱/앱 웹뷰) · 트래픽 규모의 자릿수.

추천 없이 묻는다 — 여기서 추측하면 이후 전부가 틀린 전제 위에 쌓인다.

## C2. 데이터의 성격 — 추천형

- **낡으면 틀린 값인가** (가격·재고·잔고·호가) vs 조금 낡아도 되는가(게시글·프로필)
- **개인정보·결제정보가 지나가는가** — 지나간다면 저장 금지 목록을 C6에서 확정한다
- **얼마나 자주 바뀌는가** — 초 단위/일 단위/거의 안 바뀜

➡️ 도메인에서 대부분 읽힌다. 코드베이스·API 명세를 먼저 뒤지고, 안 나오는 것만 묻는다.

## C3. 실행 환경 — 사실 조사 (묻지 말 것)

프레임워크(React/Next.js/기타) · 서버 렌더 계층 유무 · 라우터 종류 · 서버 상태 라이브러리(TanStack Query 등) 유무 · 인증 방식.

**이건 질문이 아니라 조사 항목이다.** `package.json`, 라우터 설정, 기존 유사 화면을 읽어 파악하고 "이렇게 파악했다"로 확인만 받는다. 이걸 사용자에게 물으면 스킬이 일을 안 한 것이다.

## C4. 상태를 어디에 둘까 — 추천형

같은 값이라도 살아야 하는 수명이 다르다. 후보와 수명:

| 위치 | 사는 범위 | 적합 |
|------|----------|------|
| 컴포넌트 로컬 | 마운트 동안 | 열림/닫힘, 입력 중인 값 |
| URL(경로·쿼리) | 새로고침·뒤로가기·공유·북마크 | 필터·정렬·페이지·현재 단계 |
| 서버 상태 캐시(TQ 등) | 세션 + 재방문 | 서버에서 받아온 데이터 |
| sessionStorage | 탭이 열려 있는 동안 | 임시 진행 상황 |
| localStorage | 브라우저를 바꾸기 전까지 | 사용자 설정 |
| 서버 | 영구·기기 무관 | 되면 안 되는 것이 없어야 하는 데이터 |

➡️ **원칙: "이 값이 날아가도 되는 가장 짧은 수명"을 고른다.** 필요 이상으로 오래 사는 상태는 전부 버그의 씨앗이다(옛 값이 되살아난다).
➡️ **진실은 한 곳에만.** URL에 있으면서 동시에 컴포넌트 상태에도 복사하면, 뒤로가기 때 화면과 주소가 어긋난다. → `topics/state-location.md`

## C5. 데이터를 언제 가져올까 — 추천형

서버 렌더 여부 · 캐시 필요 여부 · 요청 경쟁(빠른 연타로 이전 응답이 나중에 도착) 여부로 갈린다. 5분기 판정과 근거는 `topics/data-fetching.md`.

➡️ 기본: 캐시·경쟁·폴링 중 **하나라도** 필요하면 서버 상태 라이브러리를 쓴다. 직접 `fetch` + `useState`는 셋 다 필요 없을 때만.

## C6. 새로고침·뒤로가기·공유에서 무엇이 살아야 하나 — 추천형

이 화면을 열어둔 채 사용자가 하는 3가지: 새로고침(F5), 뒤로가기, 링크 복사해서 보내기. **각각에서 무엇이 복원돼야 하는가.**

같이 확정할 것: **URL에 절대 넣지 않을 것** — 임시 UI 상태 / 개인정보·토큰 / 타이핑 중간값 / 대용량 선택(ID 참조로 대체).

➡️ 여기서 나온 답이 C4를 되돌려 바꿀 수 있다. 바뀌면 C4를 다시 확정하고 기록한다.

## C7. 실패하면 어떻게 되나 — 필수 확인형 (돈·계약이 걸린 경우)

- 요청이 실패하면: 자동 재시도 / 수동 재시도 버튼 / 이전 상태로 되돌림 — 무엇인가
- 같은 동작이 두 번 실행되면 안 되는 것이 있는가 (결제·발송·차감)
- 요청은 성공했는데 응답을 못 받으면(네트워크 끊김) 무엇으로 확인하는가

➡️ **자동 무한 재시도는 금지.** 사용자가 상황을 모른 채 서버만 두들긴다.
➡️ 두 번 실행되면 안 되는 동작에는 클라이언트 발급 **멱등키**(같은 요청임을 서버가 알아보는 고유값)를 붙인다 — 재시도해도 결과가 하나가 된다. → `topics/submit-safety.md`

## C8. 무엇을 포기할 것인가 — 추천형

모든 결정에는 대가가 있고, 대가를 명시적으로 고르지 않으면 나중에 "이럴 줄 몰랐다"가 된다. 이번 설계에서 **의도적으로 포기하는 것**을 사용자와 합의해 결정 기록에 남긴다.

자주 등장하는 교환: SEO ↔ 무한스크롤 · 초기 로딩 속도 ↔ 상호작용 반응성 · 구현 단순함 ↔ 복구 능력 · 백엔드 협의 비용 ↔ 데이터 안전성.

➡️ 사용자가 "다 필요하다"고 하면, 셋 중 순위를 매겨 달라고 되묻는다. 순위 없는 요구는 설계가 아니라 희망이다.
