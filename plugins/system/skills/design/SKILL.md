# design — 설계 문답 진행 규칙

**설계를 대신 정해주는 스킬이 아니라, 사용자와 함께 정하는 스킬이다.** 정답이 하나뿐인 것은 못박고, 도메인·기획에 따라 갈리는 것은 추천안을 붙여 묻는다. 무엇을 물어야 하는지는 `references/core-questions.md`(모든 화면 공통)와 `references/cases/`(케이스별 추가 질문)에 있다.

## 3단계

1. **사실 조사 — 사용자에게 묻기 전에 내가 찾는다.** 프레임워크·라우터·서버 렌더 계층 유무·상태 관리 라이브러리·기존 API 명세·유사 화면의 기존 구현은 코드베이스에서 읽는다. 읽어낸 것은 질문하지 않고 "이렇게 파악했다"로 **확인만** 받는다. 조사가 오래 걸리면 그 조사에 걸린 질문만 미루고 나머지 라운드는 먼저 진행한다.
2. **라운드 문답 — 지금 답할 수 있는 질문만 묶어서 한 번에.** 아래 형식·강도 규칙을 따른다.
3. **결정 기록 — 파일로 남긴다.** 채팅 출력으로 끝내지 않는다(아래 "결정 기록" 절).

## 라운드 문답 규칙

- **프론티어 단위로 묶는다.** 지금 답할 수 있는 질문(선행 결정이 이미 끝난 것)을 **한 라운드에 모두** 낸다. 다른 질문의 답에 따라 내용이 바뀌는 질문은 이번 라운드가 아니라 **다음 라운드**다. 한 번에 하나씩 묻는 핑퐁도, 아직 못 정할 것까지 몰아 묻는 것도 금지.
- **질문마다 추천안을 반드시 붙인다.** 선택지만 나열하고 사용자에게 고르라고 던지는 것은 일을 떠넘기는 것이다. 추천이 없으면 그 질문은 "필수 확인형"(아래)이어야 하고, 왜 추천할 수 없는지를 적는다.
- **선택지에는 대가를 적는다.** 각 선택지가 무엇을 얻고 무엇을 포기하는지 한 줄씩. 근거가 긴 것은 `references/topics/`를 가리킨다.
- **신입도 읽을 수 있게 쓴다.** 약어·업계 용어는 처음 쓸 때 한 줄로 풀고, 추상적 설명 대신 그 결정이 어긋났을 때 실제로 터지는 증상으로 설명한다("뒤로가기 누르면 폼 전체가 닫힌다"처럼).
- 답을 받으면 **프론티어를 다시 계산**해 다음 라운드를 낸다. 물을 것이 없어지면 종료하고, 사용자 확인 전에는 구현에 들어가지 않는다.

라운드 형식:

```
### Q{n}. {질문 제목}

{왜 묻는지 · 무엇이 갈리는지}

- **A안: {선택지}** — 얻는 것 / 포기하는 것
- **B안: {선택지}** — 얻는 것 / 포기하는 것

➡️ **{추천안} 추천.** {근거 한두 줄}
```

## 질문 강도 3종 — 무엇을 묻고 무엇을 못박을지

| 강도 | 언제 | 어떻게 |
|------|------|--------|
| **확정형** | 업계 합의가 있고 도메인이 바꾸지 못하는 것 | 묻지 않고 결정으로 통보한다. 다르게 가려면 사용자가 근거를 대야 한다. (예: 피드 페이지네이션은 커서, 카드번호·비밀번호는 저장 금지) |
| **추천형** | 도메인·기획·팀 사정에 따라 갈리는 것 | 추천안을 붙여 묻는다. 사용자가 다르게 답하면 그대로 따르고, 대가만 기록에 남긴다. (예: 상태 보관 위치, 이어서하기 만료 기간) |
| **필수 확인형** | 틀리면 법적·금전적 손실이고 추측이 불가능한 것 | 추천 없이 반드시 묻는다. 답 없이 진행하지 않는다. (예: 결제사·PG 정책, 개인정보 보관 요건, 재고 선점 규칙) |

케이스 파일의 각 질문에는 이 강도가 표시돼 있다. **강도를 임의로 낮추지 마라** — 필수 확인형을 추천으로 때우면 사고가 난다.

## 케이스 선택

1. 요청을 읽고 `references/cases/`에서 맞는 케이스 파일을 고른다.
   - `cases/list-and-detail.md` — 목록 + 필터/정렬/검색 + 상세 왕복
   - `cases/feed.md` — 무한 스크롤 피드(타임라인·추천 콘텐츠)
   - `cases/funnel-form.md` — 여러 단계로 나뉜 퍼널 폼(주문·회원가입·온보딩·설문)
2. **맞는 케이스가 없으면 `references/core-questions.md`(범용 뼈대)만으로 진행한다.** 케이스 파일이 없다고 거절하지 않는다 — 뼈대 질문은 어떤 화면에나 성립한다.
3. 케이스가 둘 이상 걸치면(예: 피드 + 상세 왕복) 둘 다 얹는다. 중복 질문은 한 번만 묻는다.
4. 문답 중 새로 알게 된 케이스별 질문이 반복해서 유용하면, 작업 후 사용자에게 **케이스 파일에 추가할지** 제안한다.

## 결정 기록 — 문답의 산출물

문답이 끝나면 **실행 중인 프로젝트**의 `docs/design/{YYYY-MM-DD}-{기능-슬러그}.md`로 남긴다(`docs/design/`이 없으면 만들지 물어본다. 사용자가 다른 위치를 원하면 그쪽에).

```markdown
# 설계 결정: {기능명}

| 항목 | 내용 |
|------|------|
| 날짜 | {YYYY-MM-DD} |
| 케이스 | {적용한 케이스 파일 / 없으면 "범용"} |
| 범위 | {무엇을 만드는가 — 한두 줄} |

## 결정

| # | 결정한 것 | 선택 | 이유 | 포기한 것 |
|---|----------|------|------|----------|
| 1 | 단계 상태 보관 위치 | 서버 임시저장 | 거래형 + 임시저장 API 존재 | 백엔드 협의 비용 |

## 확인하지 못한 것
- {물었으나 답이 없었거나, 자율 실행이라 못 물은 항목 + 채택한 기본값}

## 나중에 뒤집힐 조건
- {"동시 접속이 10배가 되면 축 X는 재검토" 처럼, 이 결정을 무효화할 미래 조건}
```

"나중에 뒤집힐 조건"을 비워두지 마라. 결정은 상황의 함수이고, 그 상황이 적혀 있지 않으면 다음 사람이 결정을 뒤집을 근거도 지킬 근거도 갖지 못한다.

## 주의사항

- **이 스킬은 설계까지다.** 애니메이션·컴포넌트 구현 패턴(모달 전환, 스켈레톤, 제스처)은 fe-ui 스킬이 담당한다.
- **자율 실행이라 물을 수 없을 때**는 추천형 질문에 한해 추천안을 채택하고, 결정 기록의 "확인하지 못한 것"에 전부 남긴다. **필수 확인형은 기본값으로 때우지 말고 작업을 멈추고 보고한다.**
- 사용자의 답이 케이스 파일의 추천과 다르면 **한 번만 반론**하고(대가를 구체적 증상으로 제시), 그래도 유지하면 따른다. 반복해서 설득하지 않는다.
- 기존 화면 진단 요청이면 같은 질문 트리를 **검사 항목**으로 쓴다 — 증상에서 어느 결정이 잘못됐는지 역추적하고, 고칠 결정만 문답한다.
