# 복귀 복원과 새 글 병합 — 피드의 두 연속성

## A. 복귀 복원 — 최선은 "복원하지 않는 것"

상세 갔다 돌아온 피드가 살아 있으려면 세 가지가 복원돼야 한다: 로드했던 N페이지 데이터, 스크롤 위치, (가상화 시) 실측 높이 캐시. 이 셋을 저장했다 되살리는 것보다 **애초에 잃지 않는 쪽**이 항상 싸고 정확하다.

### 1순위 — 피드를 언마운트하지 않는다

상세를 피드 위의 **스택·모달로** 연다. 피드 DOM·스크롤·측정치가 그대로 살아 있으므로 복원 문제 자체가 소멸한다.

- 모바일 앱(RN 등): 스택 내비게이션이 기본 제공 — 이 판정이 자연스럽다.
- 웹: 모달 상세 + **URL 동반**(Next.js 인터셉팅 라우트 등) — 공유·새로고침 시에는 전체 상세 페이지로 열린다. `list-filter-detail` 축④와 같은 원리.
- 전제: 내비게이션 구조가 이를 지원해야 한다(신호 F7). 지원하지 않는 SPA 라우터(경로 전환 = 언마운트)면 2순위로.

### 2순위 — 근사 복원 (풀 언마운트·브라우저 뒤로가기 커버)

- **데이터**: TanStack Query `useInfiniteQuery` 캐시 — 로드한 전체 페이지가 캐시에 있으므로 복귀 시 재요청 없이 즉시 렌더된다. `staleTime`을 0으로 두면 복귀마다 전체 리페치가 일어나 복원이 깨진다 — 피드 목록은 유의미한 staleTime을 준다.
- **위치**: sessionStorage에 스크롤 오프셋 + 로드 페이지 수 기록(이탈 시점에 저장). 가상화 중이면 실측치가 사라졌으므로 추정 기반 **근사 복원**이 된다 — 몇십 px 오차는 수용한다. 완벽 복원을 좇아 실측 캐시까지 직렬화하는 것은 과설계다.
- **순서가 생명**: 데이터 복원(캐시 히트) → 높이 확보(aspect-ratio·추정) → 스크롤 이동. 데이터가 오기 전에 스크롤부터 옮기면 0높이 문서에서 이동이 무효화된다.

## B. 새 글 병합 — 읽던 줄을 지켜라

체류 중 도착한 새 글을 어떻게 반영하는가. 판정 기준은 **소비 방향**(신호 F6)이다.

### 타임라인(위→아래 소비) — 자동 삽입 금지

읽는 도중 위에 항목이 끼어들면 화면이 밀린다 — 읽던 줄을 잃는 것이 자동 삽입의 비용이고, 피드에서 이 비용은 언제나 이득보다 크다. 기본값:

- **"새 게시물 N개" 버튼** — 새 글 도착은 배지로만 알리고, 병합은 사용자가 버튼을 눌렀을 때(맨 위로 스크롤 + 삽입).
- 부득이 제자리 삽입해야 하면 **스크롤 앵커링**(삽입 높이만큼 스크롤 보정, `overflow-anchor`가 기본 동작)으로 읽던 위치를 고정한다.
- **당겨서 새로고침**은 병합이 아니라 전체 갱신이다 — 커서를 리셋하고 1페이지부터 다시 시작한다(제스처 구현은 fe-ui 몫).

### 채팅형(맨 아래 고정 소비) — 자동 append 허용

최신이 아래에 붙고 사용자가 바닥에 붙어 있는 구조에서는 자동 삽입이 곧 기대 동작이다. 단 사용자가 위로 스크롤해 과거를 읽는 중이면 고정을 풀고 "새 메시지 ↓" 버튼으로 전환한다 — 같은 원칙("읽던 줄을 지켜라")의 다른 표현이다.

## 포기하는 것

- 1순위(스택·모달)는 라우터 구조 제약을 받는다 — 구조가 안 되면 근사 복원의 오차를 수용한다.
- 수동 병합은 "실시간성 체감"을 일부 포기한다 — 초 단위 반영이 제품 핵심(시세·경기 중계)이면 이 스킬의 피드 판정이 아니라 별도 실시간 화면 설계다.
