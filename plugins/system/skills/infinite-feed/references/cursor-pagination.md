# 커서 페이지네이션 — 왜, 그리고 어떤 커서인가

## 오프셋이 피드에서 무너지는 두 지점

`?page=3&size=20`(오프셋)은 "앞에서 40개 건너뛰고 20개"라는 뜻이다. 문제는 그 "앞 40개"가 요청 사이에 변한다는 것:

1. **중복·누락.** 사용자가 2페이지를 보는 동안 맨 앞에 새 글 5개가 삽입되면, 3페이지 요청은 이미 본 항목 5개를 다시 내려보낸다(중복). 반대로 앞쪽 항목이 삭제되면 아직 안 본 항목을 건너뛴다(누락). 피드는 체류 중 삽입이 상수로 일어나는 화면이라 이 결함이 항상 발현된다.
2. **DB 비용.** `OFFSET 40`은 40행을 읽고 버린다. 깊이 스크롤할수록 선형으로 느려진다. 커서(키셋)는 정렬 인덱스를 시크해 시작점부터 읽는다.

## 삭제 안전한 커서 — "행 포인터"가 아니라 "정렬 공간의 위치 값"

커서를 "마지막 아이템의 id"로 잡고 서버가 그 행을 찾아 다음을 잇는 구현은, **그 행이 삭제되면** 기준을 잃는다. 안전한 설계는 커서에 **정렬 키 값 자체**를 담는 것이다:

```
cursor = (created_at, id)   -- id는 동시각 타이브레이커
WHERE (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
```

비교가 값끼리 이루어지므로 커서가 가리키던 행이 삭제돼도 아무 일도 생기지 않는다 — 별도 보정 로직이 필요 없다.

## 랭킹 피드 — 커서의 정체가 바뀐다

추천·인기 정렬은 점수가 요청 시점마다 바뀌어 "이 값보다 작은 것부터"라는 전제가 무너진다. 이때 커서는 **스냅샷 커서**가 된다: 첫 요청에서 서버가 랭킹 결과를 고정(스냅샷)해 두고, 커서는 그 스냅샷 안의 위치를 담는다(인스타그램·유튜브의 page token). 스냅샷에는 만료가 있고, 만료된 커서 요청은 목록 처음부터 다시 시작된다.

## FE 계약 — 불투명 토큰

값 커서와 스냅샷 커서는 백엔드 구현이 완전히 다르지만, **FE 계약은 동일하다**: 응답의 `nextCursor`를 해석·조작하지 않고 다음 요청에 그대로 되돌려준다. FE가 커서를 파싱하는 순간 백엔드의 커서 전략 교체가 프론트 배포를 요구하게 된다.

API 협의 시 FE가 백엔드에 확인할 질문:

1. 커서가 **행 존재에 의존**하는가? (의존하면 삭제 시나리오 제시 — 값 커서로 요청)
2. 정렬이 랭킹이면 **스냅샷 커서**인가? 만료 정책과 만료 시 응답은?
3. `hasNext`(또는 `nextCursor: null`)로 끝을 명시하는가?

## 그래도 중복 제거는 클라이언트 안전망으로

커서가 완벽해도 중복은 생긴다 — 스냅샷 만료 후 재시작, 새 글 병합(수동 새로고침)과 기존 페이지의 경계, 네트워크 재시도. 페이지를 이어 붙일 때 **id 기준 중복 제거**를 항상 넣는다. 비용은 Set 하나, 막는 사고는 "같은 글이 두 번 보여요"다.

## 포기하는 것

- **임의 페이지 점프** ("7페이지로 가기") — 커서는 순차 전용이다. 피드 UX에는 점프가 없으므로 실질 손실이 없다.
- **전체 개수·전체 페이지 수** — 표시가 꼭 필요하면 별도 count API로 분리한다(카운트 쿼리는 비싸다 — 근사치 협의).
