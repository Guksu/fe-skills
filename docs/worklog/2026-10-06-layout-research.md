# 레이아웃 기준 조사 — 피드백 사례 분석과 원칙 정립

| 항목 | 내용 |
|------|------|

| 작성 | 에이전트 (Claude Code) |

## 1. 개요

suta에 레이아웃 스킬과 검사 훅을 넣기 전에 기준부터 세웠다. 사용자가 고른 실무 UI 디자인 피드백 자료를 분석해 원칙을 뽑았다. 자료는 시안을 고치기 전과 후를 보여 준다. 뽑은 원칙은 에이전트가 한 번 더 정립했다(사용자 지시). 구현은 하지 않았다.

공개 문서에는 원본 자료의 출처를 적지 않는다(사용자 결정). 원본 자료와 사례별 목록은 저장소 밖에만 두었다.

## 2. 작업내용

- **사례 분석**
  - AI 에이전트가 사례마다 화면과 설명을 보고 다음을 기록했다: 주제, 화면, 수정 전후, 원칙(새로 쓴 문장), 태그, 확신도.
  - 6건 시험 분석으로 지침을 검증했다. 판단이 갈리는 세 경우의 기준을 지침에 보탰다.
    - 어느 화면을 '후'로 볼지.
    - 설명끼리 서로 다를 때.
    - 작은 화면을 확대해 볼 때.
  - 중간에 사용량 한도로 멈췄다. 배치를 39건에서 12건으로 줄이고 동시 실행을 6개로 제한해 이어 갔다.
  - 결과
    - 관련 307건: 레이아웃 223, 시각 55, UX 29.
    - 확신도: 분명 96, 일부 182, 불명 29.
    - 작업 방식·커리어 이야기와 그래픽 도구 사용법은 원칙에서 뺐다.
  - 표본은 원본과 직접 대조해 서술이 맞는지 확인했다.
- **정립(`docs/research/2026-10-06-layout-principles.md`)**
  - 관련 307건의 원칙을 모두 읽고 원칙 12개(P1~P12)로 묶었다. 순서는 순서 정하기 → 배치 → 규격 → 검증이다.
  - 원칙마다 원칙 / 왜 / AI 슬롭 증상 / 코드 기준 / 검사 가능성을 붙였다.
  - 반대로 읽히는 조언 8쌍에 판단 기준을 세웠다. 예: "여백을 과감하게" vs "의미 없는 여백", "밋밋하게" vs "힘을 줘라", "카드를 걷어라" vs "카드로 끊어라".
  - 다음 단계에 쓸 자료: 스킬 금지선 후보 21행, 정적·브라우저 검사 후보 14개.
- **출처 제거(사용자 결정)**
  - 출처를 드러내는 정보를 문서에서 모두 뺐다. 자료 이름·링크·사례 제목·사례별 목록·수집 방법이 대상이다.
  - 사례별 목록은 사용자에게 저장소 밖 파일로 따로 전했다.
  - 조사 문서는 출처를 뺀 뒤 처음 커밋하므로 git 기록에도 남지 않는다.
- **오픈소스 공개 전 법적 검토**
  - 점검 범위: 저작권, 출처 표시, 부정경쟁, 자료 제공처 약관, 상표, 라이선스.
  - 결과는 사용자에게 보고했다. 요지는 3절에 있다.
- **AGENTS.md** — 저장소 구조의 docs 설명에 `조사(research/)`를 넣었다.

## 3. 주의사항

- **저작권과 출처**
  - 원본 자료(이미지·문장)는 저장소에 넣지 않았다. 원칙은 새로 쓴 문장이다.
  - 아이디어·방법은 저작권 보호 대상이 아니다(대법원 1997. 9. 29.자 97마330 결정).
  - 출처 명시 의무(저작권법 제37조)는 인용처럼 저작물을 이용할 때 생긴다. 그래서 출처 없이 공개해도 된다고 판단했다.
  - 원본 문장·이미지나 사례별 요약을 공개 문서에 다시 넣지 않는다.
- **원본 자료**: 분석에 쓴 원본은 작업 후 지웠다. 추가 조사가 필요하면 자료를 직접 보고 정리한다.
- **근거 확인**
  - 관련 사례의 59%가 확신도 "일부"다.
  - 요점을 알 수 없었던 12건은 사용자가 확인해 주면 원칙에 반영한다(목록은 저장소 밖 파일에 있다).
- **다음 단계**(사용자 확인 후)
  - SKILL.md에 "레이아웃" 금지선을 넣는다.
  - 패턴 `layout-principles`를 만든다.
  - `layout-audit` 정적 검사와 편집 후 훅을 붙인다. 훅은 정할 것이 둘이다: 플러그인 루트 `hooks/` 가드, 그리고 Codex에서 대신할 방식.
- **브랜드명 정리(권장, 이번 범위 밖)**
