# 레이아웃 원칙 정립

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-10-06 |
| 방법 | 실무 UI 디자인 피드백 사례(시안을 고치기 전과 후)를 분석해 원칙을 뽑고, 이 문서에서 다시 묶고 정립했다(→ 6절) |
| 상태 | 초안 — 사용자 검토 전. 이 문서가 suta 레이아웃 스킬과 검사 훅의 기준이 된다 |

## 1. 한눈에

- **레이아웃·시각·UX를 다룬 피드백 사례 307건**에서 원칙을 뽑았다(레이아웃 223, 시각 55, UX 29).
- **수백 건의 피드백은 한 문장으로 모인다. "레이아웃은 꾸미는 일이 아니라 순서를 정하는 일이다."**
  - 무엇을 먼저 보게 할지, 무엇을 같이 묶을지, 무엇을 뺄지를 먼저 정한다.
  - 그 순서는 가장 값싼 수단으로 표현한다. 크기·굵기·색 농도·간격·정렬이다.
  - 비싼 수단은 한두 번만 쓴다. 채운 색 면·그림자·그라데이션·상자·장식이다.
- **AI가 만든 화면은 정확히 반대로 간다.** 모든 요소를 같은 무게로 늘어놓고, 순서를 정하는 대신 카드·그라데이션·배지로 꾸민다. 그래서 피드백에서 "망한 디자인"으로 고친 시안과 AI 슬롭(AI가 만든 티가 나는 UI)은 증상이 거의 같다(→ 4절).

## 2. 정립한 원칙 12개

화면 하나를 만들 때 적용하는 순서대로 놓았다. 1~3은 순서를 정하는 일, 4~8은 배치하는 일, 9~10은 규격, 11~12는 검증이다.

| # | 원칙 | 한 줄 | 근거 사례 |
|---|---|---|---|
| P1 | 순서부터 정한다 | 그리기 전에 요소의 순위를 매기고, 이유를 못 대는 요소는 뺀다 | 88 |
| P2 | 위계는 크기·굵기·농도로 | 순위를 글자 크기·굵기·색 농도의 눈에 띄는 차이로 보인다 | 136 |
| P3 | 강조는 한두 곳에만 | 채운 색·효과·큰 크기 같은 강한 수단은 화면마다 한두 곳 | 111 |
| P4 | 간격으로 묶는다 | 묶음 안 간격은 묶음 사이 간격의 절반 이하 | 48 |
| P5 | 상자는 마지막 수단 | 간격 → 선 → 배경 → 테두리 → 그림자 순으로, 상자는 한 겹만 | 62 |
| P6 | 정렬선 하나, 읽는 방향 하나 | 왼쪽 선 하나에 맞추고, 숫자는 오른쪽 한 열, 지그재그 금지 | 64 |
| P7 | 줄이지 말고 덜어낸다 | 자리가 모자라면 글자가 아니라 요소·열을 줄인다 | 42 |
| P8 | 빈 곳은 의도로만 | 여백은 묶음을 가르고 초점을 띄울 때만, 늘려서 생긴 빈 곳은 안 된다 | 99 |
| P9 | 사진은 가리지 않고 비율을 지킨다 | 사진 위에 글을 얹지 않고, 비율 틀을 정해 늘이지 않는다 | 67 |
| P10 | 규격을 정하고 반복한다 | 반복 단위는 컴포넌트 하나, 값은 토큰에서만 | 75 |
| P11 | 익숙한 구조에서 시작한다 | 구조는 관례를 따르고, 개성은 한 요소의 크기로 낸다 | 33 |
| P12 | 실제 데이터와 크기로 확인한다 | 가장 긴 값·빈 값·오류·좁은 폭으로 시험한다 | 27 |

"근거 사례"는 분석 태그와 핵심어로 센 근사치다. 한 사례가 여러 원칙에 걸릴 수 있다.

원칙마다 다음 순서로 적는다.
- **원칙**: 지킬 것.
- **왜**: 안 지키면 사용자에게 생기는 문제.
- **AI 슬롭 증상**: AI가 흔히 만드는 모습.
- **코드 기준**: CSS 값과 구조로 옮긴 것.
- **검사**: 기계로 잡을 수 있는지(정적 검사 = 코드만 읽고 판정, 브라우저 검사 = 렌더한 화면에서 판정, 사람 판단).

### P1. 순서부터 정한다

- **원칙**
  - 화면을 그리기 전에 들어갈 요소를 목록으로 뽑고 순위를 매긴다.
  - 1순위는 하나다. 사용자가 이 화면에 온 이유이거나, 이 화면에서 해야 할 일이다.
  - 넣을 이유를 한 문장으로 말할 수 없는 요소는 뺀다. 장식 그래픽, 화면 목적과 무관한 메뉴, 같은 말을 되풀이하는 덩어리가 그 대상이다.
  - 배너·메인처럼 훑고 지나가는 화면은 전할 메시지를 하나로 좁힌다.
- **왜**: 순위가 없으면 모든 요소가 같은 무게로 놓인다. 그러면 사용자가 무엇부터 볼지 스스로 골라야 한다.
- **AI 슬롭 증상**
  - 요청과 상관없이 정해진 틀을 채운다. 예: 히어로 → 기능 카드 3장 → 후기 → CTA.
  - 모든 필드를 같은 크기·같은 카드로 나열한다.
  - 장식용 blob·물결·3D 오브젝트를 넣는다.
- **코드 기준**
  - 화면마다 1순위 요소가 하나다. 가장 큰 글자는 하나이고, 채운 주 버튼도 하나다.
  - 장식 요소는 넣는 이유를 주석 한 줄로 쓸 수 있을 때만 넣는다.
- **검사**: 사람 판단. 결과는 P2·P3 검사로 간접 확인한다.

### P2. 위계는 크기·굵기·농도로

위계는 무엇을 먼저 읽을지의 순서다.

- **원칙**
  - P1의 순위를 글자 크기·굵기·색 농도로 표현한다.
  - 한 덩어리(카드·구역) 안의 글자는 3단계 안팎이다(주·본문·보조).
  - 단계 사이 차이는 눈에 띄어야 한다.
    - 핵심 수치는 라벨의 2~3배.
    - 화면 제목은 본문의 1.5배 이상.
    - 섹션 제목은 페이지 제목보다 한 단계 낮다.
  - 핵심 값은 문장 속에 끼우지 않는다. 자기 줄에 두고, 라벨은 위에 작게, 변화량은 아래에 작게 붙인다.
  - 보조 정보는 작고 옅게 낮춘다. 단, 색과 굵기를 둘 다 약하게 하지 않는다. 색을 연하게 하면 굵기를 한 단계 올리고, 가늘게 하면 색을 진하게 한다.
- **왜**: 글이 모두 비슷한 무게면 내용이 다 보여도 읽을 순서가 정해지지 않는다. 반대로 보조 글이 너무 옅으면 비활성처럼 읽혀 확인을 빠뜨린다.
- **AI 슬롭 증상**
  - 지표 숫자와 라벨이 비슷한 크기다.
  - 라벨·이름까지 모두 굵게 한다.
  - 섹션 제목이 페이지 제목만큼 크다.
  - 보조 글을 회색 바탕 위 옅은 회색으로 둔다.
- **코드 기준**
  - 글자 크기는 토큰(이름 붙인 공용 값)에서만 고른다. 한 화면에 역할 수만큼, 보통 4~5종이다.
  - 굵기는 3종이다(예: 400·600·700).
  - 보조 글자색의 명암비는 배경 대비 4.5:1 이상이다. 큰 글자(약 24px, 굵으면 약 19px 이상)는 3:1이다(WCAG 1.4.3).
- **검사**
  - 정적: 파일·컴포넌트마다 font-size 종류 수와 font-weight 종류 수를 센다.
  - 브라우저: 렌더된 글자 크기 종류와 글자 대비를 잰다.

### P3. 강조는 한두 곳에만

- **원칙**
  - 강한 수단은 화면(또는 구역)마다 가장 중요한 한두 곳에만 쓴다. 강한 수단은 채운 강조색 면, 그림자, 그라데이션, 유리(반투명 흐림)·광택 효과, 아주 큰 크기다.
  - 강한 수단을 쓴 곳을 세어 본다. 둘 이상이면 하나만 남긴다.
  - 강조색으로 채운 버튼은 주 행동 하나다.
    - 보조 행동은 윤곽선 버튼이나 글자 링크로 둔다.
    - 부가 태그·배지는 회색 글자나 옅은 테두리로 둔다.
    - 같은 비중의 카드 묶음에 카드마다 다른 원색을 주지 않는다.
  - 항상 떠 있는 하단 탭·바는 중립색으로 두고, 효과를 넣지 않는다.
  - 색만으로 뜻을 전하지 않는다. 색상 칩에는 이름을 함께 쓴다.
- **판단 기준**: "밋밋하게 하라"와 "힘을 줘라"는 부딪히지 않는다(→ 3절).
  - 밋밋해 보이는 원인은 모든 요소가 같은 무게라는 데 있다.
  - 해결은 전부에 볼륨을 주는 게 아니라, 한두 곳에만 주는 것이다.
- **왜**: 강조가 여럿이면 서로 시선을 나눠 가져서, 결국 아무것도 강조되지 않는다.
- **AI 슬롭 증상**
  - 그라데이션 글자·버튼·배경을 여러 곳에 쓴다.
  - 아이콘마다 색 원 배경을 깐다.
  - 카드마다 색 배지·알약 태그를 단다.
  - 같은 채움 버튼이 둘 이상이다.
  - 모든 카드에 그림자나 글래스 효과를 입힌다.
- **코드 기준**
  - 컴포넌트당 강조색 배경은 한 곳(주 버튼)이다.
  - 화면 전체에서 `linear-gradient`·`backdrop-filter`·큰 `box-shadow`는 한두 곳이다.
  - `background-clip: text`(그라데이션 글자)는 쓰지 않는다.
  - 배지는 `background: transparent` 또는 아주 옅은 배경에 보조 글자색을 쓴다.
- **검사**: 정적. 그라데이션·backdrop-filter·그림자·강조색 배경이 파일·컴포넌트마다 몇 번 나오는지 센다.

### P4. 간격으로 묶는다

- **원칙**
  - 같은 묶음 안 간격은 묶음 사이 간격보다 확실히 좁게 둔다. 절반 이하로 하고, 구역 사이는 안쪽 간격의 2~4배로 둔다.
  - 같이 읽히는 짧은 정보는 한 줄로 모은다. 예: 작성자+날짜, 장소+날짜. 사이는 얇은 세로선 하나로 나눈다.
  - 같이 쓰는 컨트롤은 한 덩어리로 합친다. 예: 검색창 안의 스캔 버튼, 칸으로 나눈 트레이 하나.
  - 판단에 필요한 정보는 그 대상 옆에 둔다. 도움말은 관련 입력 바로 아래에, 이름·가격·구매 버튼은 가까이 둔다.
  - 빈 공간은 묶음 사이에 둔다. 제목과 그 내용 사이에 두면 둘이 따로 읽힌다.
- **왜**: 사람은 가까이 있는 것을 한 묶음으로 읽는다(근접). 간격이 모두 같으면 선이나 상자를 더해야 묶음이 보이고, 화면이 무거워진다.
- **AI 슬롭 증상**
  - 모든 간격이 같은 값이다(예: `gap-6`, `p-6` 균일).
  - 관련 정보를 카드 네 귀퉁이에 흩어 놓는다.
- **코드 기준**
  - 간격은 척도에서만 고른다(예: 4·8·12·16·24·32·48·64px).
  - 묶음 안 `gap` ≤ 묶음 사이 `gap`의 1/2.
- **검사**
  - 정적: 척도 밖 간격 값을 찾는다.
  - 브라우저: 형제 요소 간격이 전부 같은 화면을 경고한다(휴리스틱).

### P5. 상자는 마지막 수단

- **원칙**
  - 나누는 수단에는 순서가 있다: 간격 → 정렬 → 얇은 선 → 배경 톤 → 테두리 → 그림자. 앞 단계로 되면 뒤로 가지 않는다.
  - 상자를 쓰지 않는 곳
    - 목록 항목마다 상자를 씌우지 않는다.
    - 상자 안에 상자를 넣지 않는다. 카드 안 카드, 회색 위 회색이 그 예다.
    - 핵심 값을 어두운 상자나 배경 띠에 가두지 않는다. 숫자 자체를 키운다.
    - 머리 영역(제목·필터·경로)과 메뉴는 상자로 띄우지 않는다.
  - 카드는 따로 열리거나 서로 비교되는 독립 단위에만 쓴다.
  - 누르지 않는 라벨을 알약 버튼처럼 만들지 않는다.
- **판단 기준**: 카드를 쓸지는 먼저 카드를 걷어 낸 상태에서 크기·굵기·정렬만으로 위계가 서는지 보고 정한다.
  - 카드를 쓴다: 피드·상품처럼 반복되는 독립 단위, 글이 길어 끊어 읽어야 하는 항목.
  - 카드를 쓰지 않는다: 이미 한 면(시트·팝업·카드) 안에 있는 행.
- **왜**: 상자는 테두리·배경만 늘리고 안쪽 폭을 줄인다. 상자가 겹치면 시선이 테두리마다 끊기고, 내용보다 상자가 먼저 보인다.
- **AI 슬롭 증상**
  - 모든 섹션·목록 행을 `rounded-xl border shadow-sm` 카드로 감싼다.
  - 카드 안에 배경 있는 상자를 또 넣는다.
  - 대시보드를 상자 9조각으로 쪼갠다.
- **코드 기준**
  - 테두리·그림자·배경이 있는 상자 안에 같은 종류 상자를 두지 않는다.
  - 목록 행은 `border-bottom` 한 줄이나 `gap`으로 나눈다.
- **검사**
  - 정적: JSX 클래스나 CSS 규칙에서 모서리 반경 + 테두리/그림자/배경을 가진 요소가 조상·자손에 겹치는지 본다.
  - 브라우저: 계산된 스타일로 보이는 상자의 중첩 깊이를 잰다.

### P6. 정렬선 하나, 읽는 방향 하나

- **원칙**
  - 화면의 정렬 기준을 하나로 정한다. 콘텐츠 화면은 왼쪽 정렬로, 제목·본문·카드·버튼이 같은 왼쪽 선에서 시작한다.
  - 가운데 정렬은 한 줄짜리 짧은 문구에만 쓴다(빈 상태 안내, 짧은 표지 문구).
  - 숫자(금액)는 오른쪽 끝 한 열에 맞춰 위아래로 비교되게 한다. 합계는 맨 아래에 가는 선 하나를 두고 굵게 둔다(영수증 형식).
  - 하위 항목은 상위 항목의 글자 시작선에 맞춘다. 썸네일 옆 글 묶음은 썸네일의 위·아래 끝에 맞춘다.
  - 시선은 위에서 아래로 한 방향으로 흐르게 한다. 요소를 카드의 다른 모서리에 흩거나, 항목을 축 위아래로 번갈아 놓지 않는다(지그재그).
- **왜**: 정렬 기준이 섞이면 줄마다 시작점이 달라진다. 그러면 시선이 지그재그로 움직이고 읽는 순서가 모호해진다.
- **AI 슬롭 증상**
  - 제목·문단·카드 글을 모두 가운데 정렬한다.
  - 금액을 왼쪽 정렬하고 비례폭 숫자로 쓴다.
  - 섹션마다 컨테이너 폭이 다르다.
- **코드 기준**
  - 기본은 `text-align: start`다.
  - 금액 열은 `text-align: right; font-variant-numeric: tabular-nums;`로 쓴다(숫자 폭을 같게 맞추는 글꼴 설정).
  - 섹션 컨테이너의 최대 폭과 좌우 안쪽 여백은 토큰 하나로 쓴다.
- **검사**
  - 정적: 여러 줄 글 요소에 `text-align: center`·`text-center`가 붙었는지 본다(휴리스틱).
  - 브라우저: 서로 다른 왼쪽 끝 x좌표가 몇 개인지 센다.

### P7. 줄이지 말고 덜어낸다

- **원칙**
  - 자리가 모자라면 글자·아이콘을 줄이지 않는다. 요소 수나 열 수를 줄인다.
  - 지금 필요한 것만 보이게 하고, 나머지는 다른 방법으로 넘긴다. '더 보기', 가로 넘김, 접힌 막대가 그 방법이다. 예: 12장 격자 → 한 줄 3~4장 + 더 보기.
  - 최소 크기를 지킨다.
    - 모바일 본문은 14px 이상이다(긴 글은 16px 권장).
    - 보조 글자도 12px 아래로 내리지 않는다.
    - 누르는 영역은 44px 이상이다.
    - 아바타는 얼굴이 구분되는 크기(28px 안팎)로 둔다.
  - 내용이 많아 스크롤이 길어지는 것은 감수한다. 좁은 영역에 욱여넣지 않는다.
- **왜**: 줄여 넣은 요소는 있어도 읽히지 않아, 없는 것과 같아진다.
- **AI 슬롭 증상**
  - 대시보드에 같은 무게의 KPI 카드를 8장 넣는다.
  - 모바일에서 4열 카드를 유지하고 글자를 9px까지 줄인다.
  - 한 화면에 모든 기능을 펼친다.
- **코드 기준**
  - font-size 12px 미만은 쓰지 않는다.
  - 누르는 요소는 `min-block-size: 44px`이거나 패딩으로 같은 영역을 확보한다. WCAG 2.2 최소 기준은 24px이고, Apple 권장값은 44pt다.
  - 카드 격자는 글자가 최소 크기를 지키는 열 수로 둔다(`repeat(auto-fill, minmax(…, 1fr))`).
- **검사**
  - 정적: 12px 미만 font-size를 찾는다.
  - 브라우저: 44px 미만 터치 대상을 찾고, 320px 폭에서 넘침을 본다.

### P8. 빈 곳은 의도로만

- **원칙**
  - 여백은 묶음을 가르고 초점 요소를 띄우는 데 쓴다. 이때는 과감하게, 처음 떠오른 값보다 넓게 시작해 줄여 나간다.
  - 화면을 채우려고 요소를 늘려서 생긴 빈 곳은 의미 없는 여백이다.
  - 카드와 글 덩어리에는 최대 폭을 둔다. 넓은 화면은 요소를 늘이지 않고 열을 늘려 채운다.
  - 답답해 보이면 장식이나 선을 더하기 전에 구역 사이 간격부터 넓힌다. 그래도 답답하면 개수를 줄이고 남은 것을 크게 쓴다.
  - 초점 요소는 생각보다 크게 잡는다. 히어로 제목이 그 예다. 작게 시작해 키우면 결과가 소심해진다.
- **판단 기준**: 빈 곳이 무엇을 가르거나 무엇을 띄우는지 묻는다(→ 3절).
  - 답할 수 있으면 의도된 여백이다.
  - 늘린 요소 안에 남은 빈 곳이면 의미 없는 여백이다.
- **왜**: 의미 없는 여백은 화면을 헐겁게 하고, 정작 필요한 곳의 여백은 모자라게 만든다.
- **AI 슬롭 증상**
  - 카드 하나를 1200px 폭으로 늘린다.
  - 섹션 위아래 패딩이 내용과 상관없이 거대하다.
  - 답답한 화면에 테두리를 더 긋는다.
- **코드 기준**
  - 글 덩어리는 `max-inline-size: 65ch` 안팎으로 둔다.
  - 카드는 `max-inline-size`를 둔다.
  - 넓은 화면의 열 추가는 `grid-template-columns: repeat(auto-fill, minmax(…, 1fr))`로 한다.
- **검사**
  - 브라우저: 한 줄 80자를 넘는 본문을 찾는다.
  - 내용에 비해 빈 면적이 큰 카드도 찾는다(휴리스틱).

### P9. 사진은 가리지 않고 비율을 지킨다

- **원칙**
  - 사진이 주인공이면 글·버튼·카드를 사진 위에 얹지 않는다. 사진 아래나 옆 빈 곳으로 뺀다.
  - 꼭 얹어야 하면 스크림(글자를 읽히게 까는 반투명 막)을 깐다. 농도는 피사체가 알아보이는 정도에서 멈춘다.
  - 이미지 비율을 정해 두고 지킨다.
    - 고정 비율 틀에 넣고 잘라 채운다. 가로·세로를 따로 늘이지 않는다.
    - 한 목록은 한 비율, 사이트 전체는 2~3개 비율만 쓴다.
  - 같은 역할의 사진은 색감·배경·피사체 위치를 맞춘다.
  - 이미지가 없을 때의 대체 모습(실루엣·이니셜)을 같은 크기로 만든다.
- **왜**
  - 사진을 가리면 사진을 쓴 이유가 사라진다.
  - 비율이 섞이면 줄이 들쭉날쭉해진다. 운영자도 사진을 올릴 때마다 비율별로 따로 잘라야 한다.
- **AI 슬롭 증상**
  - 복잡한 히어로 사진 위에 흰 글자를 바로 얹는다.
  - 이미지가 늘어나 찌그러진다.
  - 섹션마다 비율이 다르다.
- **코드 기준**
  - 이미지는 `aspect-ratio`와 `object-fit: cover`로 넣는다.
  - 오버레이 글자 아래에는 `linear-gradient` 스크림을 깐다.
  - `<img>`에 `width`·`height`를 준다(자리 확보).
- **검사**
  - 정적: `object-fit: fill`이나 비율 지정이 없는 이미지를 찾는다.
  - 브라우저: 원본 비율과 표시 비율의 차이를 잰다.

### P10. 규격을 정하고 반복한다

- **원칙**
  - 반복되는 단위는 컴포넌트 하나로 만들어 어디서나 쓴다. 상품 카드·목록 행·입력칸·버튼이 그렇다. 구역마다 달라지는 것은 크기뿐이다.
  - 다음 값은 토큰으로 정하고 그 안에서만 고른다.
    - 글자 크기·굵기
    - 역할별 색(주 색 1개, 회색 단계, 상태 색)
    - 간격, 모서리 반경, 이미지 비율
    - 아이콘 스타일(선/면 하나, 같은 격자, 같은 선 굵기)
  - 같은 역할은 같은 값을 쓴다.
    - 입력칸과 옆 버튼은 높이·반경을 한 세트로 정한다.
    - 상태(기본·hover·focus·오류)가 바뀌어도 크기는 그대로 두고, 색·테두리만 바꾼다.
- **왜**: 눈대중으로 정하면 같은 역할이 화면마다 조금씩 달라진다. 그러면 사용자는 다른 종류로 읽고, 구현도 둘로 갈라진다.
- **AI 슬롭 증상**
  - 모서리 반경 8·12·16·24px이 섞인다.
  - 섹션마다 카드 스타일이 다르다.
  - #181818과 #151515처럼 눈에 안 띄게 다른 값이 섞인다.
  - 출처가 다른 아이콘이 섞인다.
- **코드 기준**
  - CSS 변수 토큰을 쓴다. 컴포넌트에서는 리터럴 값 대신 변수만 참조한다.
  - 반경 토큰은 2~3개다.
  - 같은 역할의 버튼·입력칸은 같은 높이다(예: 48px).
- **검사**: 정적. 서로 다른 radius 값 수, 토큰 밖 색 리터럴, 척도 밖 px를 찾는다.

### P11. 익숙한 구조에서 시작한다

- **원칙**
  - 독특한 배치를 고안하기 전에 같은 종류 서비스의 화면을 여러 개 놓고 본다. 공통된 요소 순서와 위치를 기본 구조로 삼는다.
  - 관례를 따른다.
    - 로그인: 로고 → 입력 → 보조 줄 → 전체 폭 버튼 → 소셜(전체 폭 세로 쌓기).
    - 탭: 글자 + 밑줄.
    - 하단 탭바: 같은 폭 칸.
    - 합계: 영수증 형식.
    - 검색창: 돋보기·지우기 버튼.
    - 갤러리: 위치 표시(1/6).
  - 벤치마킹할 때는 겉모양이 아니라 들어 있는 요소와 그 이유를 목록으로 뽑아 대조한다.
  - 개성은 구조가 아니라 핵심 요소 하나의 크기·사진으로 낸다.
- **판단 기준**: 과감함과 익숙함은 층이 다르다(→ 3절). 구조는 익숙하게, 힘은 크기로 준다.
- **왜**: 낯선 배치는 이해에 시간이 들어 개성보다 혼란으로 읽힌다. 독특한 구조는 하나씩 쌓이면 일부만 고칠 수 없어 통째로 다시 만들게 된다.
- **AI 슬롭 증상**
  - 근거 없는 잡지식 콜라주나 비대칭 배치를 쓴다.
  - 탭을 채운 알약 버튼으로 만든다.
  - 소셜 로그인을 반 폭 버튼 둘로 나란히 놓는다.
- **코드 기준**
  - 탭은 `role="tablist"`에 선택 밑줄로 만든다.
  - 하단 탭은 `flex: 1` 같은 폭 칸이다.
  - 대등한 선택지는 전체 폭 세로 쌓기로 둔다.
- **검사**: 사람 판단.

### P12. 실제 데이터와 크기로 확인한다

- **원칙**
  - 이상적인 짧은 예시 하나로 끝내지 않는다. 다음 경우를 모두 넣어 시험한다.
    - 가장 짧은 값, 가장 긴 값(긴 이름·자릿수 많은 금액), 두 줄로 꺾이는 값.
    - 빈 값, 오류 문구가 모두 붙은 상태, 이미지 없음, 키보드가 올라온 상태.
  - 폭은 320px(가능하면 280px)부터 큰 화면까지 본다. 높이가 짧은 기기에서는 주 버튼이 첫 화면에 남는지 본다.
  - 넘칠 때의 처리를 미리 정한다(줄바꿈 / 말줄임 / 고정 요소 자리 확보).
  - 시트·모달 같은 레이어는 최대 높이를 먼저 정한다. 화면의 80% 이상을 덮게 되면 전체 화면으로 연다.
- **왜**: 보이는 한 모습에 맞춘 구조는 실제 데이터에서 깨진다. 그러면 처음부터 다시 짜야 한다.
- **AI 슬롭 증상**
  - "Lorem ipsum", "John Doe", 짧은 영어 이름으로만 만든 화면이 한국어 긴 이름·큰 금액에서 깨진다.
  - 빈 상태와 오류 상태가 없다.
  - 고정 px 열 폭이 다른 기기에서 어긋난다.
- **코드 기준**
  - 줄일 수 있는 flex 자식에는 `min-inline-size: 0`을 준다.
  - 한 줄 말줄임은 `overflow: hidden; text-overflow: ellipsis; white-space: nowrap;`이다.
  - 여러 줄은 `-webkit-line-clamp`를 쓰고, 긴 단어는 `overflow-wrap: anywhere`로 끊는다.
  - 칩·행 높이는 고정하고, 고정 영역은 안쪽 스크롤로 처리한다.
  - 열 폭은 고정 px 대신 `fr`로 나눈다.
- **검사**: 브라우저. 긴 값 데이터로 렌더해 넘침·겹침을 찾고, 320px에서 가로 스크롤을 본다.

## 3. 부딪히는 조언과 판단 기준

같은 피드백 사례들 안에서도 조언이 반대로 읽히는 경우가 있다. 맥락을 나눠 보면 모순이 아니다. 기준은 다음과 같다.

| 한쪽 | 다른 쪽 | 판단 기준 |
|---|---|---|
| 여백을 과감하게 넓혀라 | 의미 없는 여백은 쓸모없다 | 빈 곳이 묶음을 가르거나 초점을 띄우면 의도된 여백이다. 요소를 늘려서 생긴 안쪽 빈 곳은 의미 없는 여백이다. 빈 곳의 위치도 본다. 제목과 그 내용 사이가 아니라 묶음 사이에 둔다 |
| 밋밋하게 하라 | 힘·볼륨을 줘라 | 밋밋함의 원인은 모든 요소가 같은 무게라는 데 있다. 기본은 단순하게 두고, 볼륨은 한두 곳에만 준다 |
| 글자를 줄이지 마라 | 보조 글자는 작고 옅게 낮춰라 | 줄이는 것은 보조 정보뿐이다. 그것도 읽을 수 있는 하한(12px, 대비 4.5:1) 위에서다. 주 콘텐츠는 표준 크기를 지킨다. 색과 굵기를 둘 다 약하게 하지 않는다 |
| 카드를 걷어 내라 | 카드로 끊어 읽게 하라 | 카드는 한 겹만 쓴다. 독립적으로 열리거나 비교되는 단위, 끊어 읽어야 하는 긴 항목에는 쓴다. 이미 묶인 면 안의 행, 머리 영역, 메뉴에는 쓰지 않는다 |
| 덜어내라 | 필요한 정보는 남겨라 | 지우는 기준은 "이 화면의 목적에 쓰이는가"다. 쓰이는 정보는 남기고 같은 폭·간격·순서의 반복으로 정돈한다 |
| 과감하게 키워라 | 평범하고 익숙하게 하라 | 층이 다르다. 구조는 익숙하게, 힘은 한 요소의 크기로 준다 |
| 크기가 다른 카드를 어긋나게 놓아라 | 카드를 흩뿌리지 마라 | 크기 차이로 강약을 줄 때도 바깥 윤곽선과 카드 안 구성은 맞춘다. 운영 중 사진·개수가 바뀌는 목록은 같은 규격으로 둔다 |
| 같은 줄의 카드는 같은 크기로 | 같은 크기 상자만 반복하지 마라 | 같은 종류의 반복 단위(목록)는 같은 크기다. 구역 단위 배치는 큰 것 하나와 작은 것 여럿으로 중요도를 보인다 |

## 4. AI 슬롭 대응표 — 스킬 금지선 후보

`skills/suta/SKILL.md`의 "AI 슬롭 금지선"에 "레이아웃" 묶음으로 넣을 후보다. 행마다 원칙과 근거가 있다.

| AI가 흔히 하는 것 | 대신 | 원칙 |
|---|---|---|
| 모든 섹션·목록 행을 테두리+그림자+둥근 카드로 감싼다 | 간격과 얇은 선으로 묶는다. 카드는 독립 단위에 한 겹만 | P5 |
| 카드 안에 배경 있는 상자를 또 넣는다 | 상자는 한 겹. 안쪽은 간격·정렬로 나눈다 | P5 |
| 모든 간격이 같은 값이다 | 묶음 안 간격 ≤ 묶음 사이 간격의 1/2 | P4 |
| 제목·문단·카드 글을 모두 가운데 정렬한다 | 왼쪽 정렬, 하나의 왼쪽 선. 가운데는 짧은 한 줄만 | P6 |
| 금액을 왼쪽 정렬하거나 문장 속에 넣는다 | 오른쪽 끝 한 열 + `tabular-nums`. 핵심 값은 자기 줄에 | P6·P2 |
| 지표 숫자와 라벨이 비슷한 크기다 | 숫자는 라벨의 2~3배, 라벨은 작은 회색 | P2 |
| 라벨·이름까지 모두 굵게 한다 | 굵기 3종. 굵게는 영역마다 한 줄 | P2 |
| 그라데이션·글로우·글래스를 여러 곳에 쓴다 | 강한 효과는 화면마다 한 곳 | P3 |
| 채운 강조색 버튼이 여러 개다 | 채움은 주 행동 하나. 나머지는 윤곽선·글자 링크 | P3 |
| 카드마다 색 배지·알약 태그를 단다 | 회색 글자나 옅은 테두리 | P3 |
| 카드마다 다른 원색을 준다 | 강조색 하나, 한 장에만 | P3 |
| 아이콘마다 색 원 배경을 깐다 | 배경 없는 단색 아이콘, 글자 크기 수준 | P3·P10 |
| 화면을 채우려 카드·이미지를 폭 가득 늘린다 | 최대 폭을 두고 열을 더한다 | P8 |
| 좁은 화면에서 열을 유지하고 글자를 줄인다 | 열을 줄이고 본문 14px 이상 | P7 |
| 사진 위에 글·버튼을 바로 얹는다 | 사진 밖으로 뺀다. 얹을 때는 스크림 | P9 |
| 이미지 비율이 제각각이거나 늘어난다 | `aspect-ratio` + `object-fit: cover`, 비율 2~3개 | P9 |
| 이상적인 짧은 더미 데이터로만 만든다 | 가장 긴 값·빈 값·오류·320px로 확인 | P12 |
| 옅은 회색 작은 글자, 회색 위 회색 | 대비 4.5:1. 색과 굵기를 둘 다 약하게 하지 않는다 | P2 |
| 장식 blob·물결·3D 오브젝트를 넣는다 | 넣을 이유를 한 문장으로 못 대면 뺀다 | P1 |
| 탭을 알약 버튼으로, 낯선 배치를 고안한다 | 관례(밑줄 탭, 같은 폭 탭바, 영수증 합계) | P11 |
| 반경·색·간격 값이 제각각이다 | 토큰에서만 고른다 | P10 |

## 5. 기계로 검사할 수 있는 것 — 훅 후보

`motion-audit`처럼 편집한 파일을 검사하는 `layout-audit`의 후보 규칙이다. "정적"은 코드(CSS·JSX 클래스)만 읽고 판정하고, "브라우저"는 렌더한 화면에서 판정한다.

| 검사 | 방식 | 기준(초안) | 원칙 | 오탐 위험 |
|---|---|---|---|---|
| 카드 안 카드 | 정적 / 브라우저 | 반경 + 테두리·그림자·배경을 가진 요소의 자손에 같은 조합 | P5 | 중간 — 카드 안 입력칸처럼 의도된 경우 |
| 간격 척도 밖 값 | 정적 | margin·padding·gap이 척도(4의 배수·토큰)에 없음 | P4·P10 | 낮음 |
| 글자 크기 종류 | 정적 / 브라우저 | 컴포넌트 하나에 5종 초과 | P2·P10 | 중간 |
| 굵기 종류 | 정적 | 4종 이상 | P2 | 낮음 |
| 12px 미만 글자 | 정적 / 브라우저 | font-size < 12px | P7 | 낮음 |
| 강한 효과 개수 | 정적 | gradient·backdrop-filter·큰 box-shadow가 파일마다 2곳 초과, `background-clip: text` | P3 | 중간 |
| 여러 줄 글 가운데 정렬 | 정적(휴리스틱) / 브라우저 | 두 줄 이상 블록에 `text-align: center` | P6 | 중간 |
| 이미지 비율 | 정적 | 이미지에 `aspect-ratio`·`object-fit`이 없거나 `object-fit: fill` | P9 | 중간 |
| 반경 종류 | 정적 | 서로 다른 border-radius 값 4종 이상 | P10 | 낮음 |
| 색 리터럴 | 정적 | 컴포넌트 안 hex·rgb 리터럴(토큰 밖) | P10 | 중간 |
| 글자 대비 | 브라우저 | 대비 < 4.5:1(큰 글자 3:1) | P2 | 낮음 |
| 터치 영역 | 브라우저 | 누르는 요소 < 44×44px | P7 | 낮음 |
| 좁은 폭 넘침 | 브라우저 | 320px에서 가로 스크롤·잘림 | P12 | 낮음 |
| 본문 줄 길이 | 브라우저 | 한 줄 80자 초과 | P8 | 중간 |

기계로 판정하기 어려운 것도 있다. P1의 순위, P11의 관례, P8에서 여백이 의도인지는 사람 판단이다. 스킬 본문의 작업 절차와 체크리스트가 맡는다.

## 6. 방법과 한계

- **분석**
  - 피드백 사례마다 AI 에이전트가 화면과 설명을 보고 주제·수정 전후·원칙·확신도를 기록했다.
  - 원칙은 원본 문장을 옮기지 않고 새로 썼다.
  - 표본 몇 건은 원본과 직접 대조해 서술이 맞는지 확인했다.
- **정립**: 분석 결과 307건을 다시 읽고 비슷한 원칙을 합쳐 12개로 묶었다. 부딪히는 조언에는 판단 기준을 세웠다. 원칙마다 코드 기준과 검사 가능성을 붙였다.
- **한계**
  - 사례마다 화면 일부만 볼 수 있었다. 그래서 관련 사례의 59%는 확신도가 "일부"다(전후 중 한쪽만 보이거나 일부를 추정).
  - 특정 실무 관점에 기반하고, 시안은 한국 커머스·핀테크·콘텐츠 앱이 많다. 일반 원칙과 연결해 보정했다. 근접·정렬·대비·반복, WCAG 대비·터치 영역이 그 예다.
  - "근거 사례" 수는 태그와 핵심어로 센 근사치다.
- **저작권**: 원본 자료(이미지·문장)는 저장소에 넣지 않았다. 원칙은 새로 쓴 문장이다.
